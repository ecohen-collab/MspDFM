Yooz Rising (eu1.getyooz.com, app GUID `a99d3a57-2207-4f95-96a1-6017ff5ae393`, API base `/yooz/v2/api/`). Étend [[project_yooz_factures_tdsynnex]]. Découvert 2026-06-25 en câblant l'auto-validation.

**Valider (≠ brouillon)** : sur `POST /yooz/v2/api/documents`, deux leviers combinés :
1. `documentFullyProcessed=true` (form field) → Yooz traite le doc comme complet (validation STRICTE).
2. Bloc `documentTimeline` (frère de `data` dans le JSON) : `[{YZ_USER:{value:email}, YZ_WORKFLOW_STEP_NAME:{value:"<étape>"}, YZ_USER_TASK_VALIDATION_DATETIME:{value:"YYYY-MM-DD HH:MM:SS.mmm"}}]` → marque l'étape comme validée. Codé dans `yooz_client.submit_document(..., validate_step=, validator=)` + UI case « Valider auto » + champ étape (yooz.html).

**Dimensions analytiques (NON RÉSOLU — bloqué)** : en mode `fullyProcessed`, le bloc `YZ_INVOICE_LINE` valide STRICTEMENT et REJETTE tous les codes de champ dimension essayés (`UNKNOWN_DATA_ITEM_FOR_GIVEN_CONFIGURATION`) : `YZ_DIMENSION_AGENCE`, `YZ_DIMENSION_METIER`, `AGENCE`, `METIER`, `dimensions`, `YZ_DIMENSION_CODE` (ça = YZ_ORDER_LINE commande), `YZ_DIMENSION_AXE01`/`AXE02` (exemple générique du manuel p.30, pas valable ici). Yooz NE DÉRIVE PAS l'analytique tout seul (testé rev 0099 : doc créé sans champ dimension → agence ET métier VIDES). Le vrai code du data item est **config-interne, introuvable** : absent du swagger (POST /documents = multipart générique), des exports, de tous les endpoints lisibles. → **Demander à Benjamin / support Yooz** le code exact du data item AGENCE/MÉTIER du bloc YZ_INVOICE_LINE en import. Une fois connu : 1 ligne dans `submit_document` (chemin validate) ou via `POST /feedbacks` (modifier doc existant : {yoozNumber, fieldsToUpdate:[{dataBlockCode, dataItemCode, value}]}). En brouillon les flat keys étaient IGNORÉES (d'où « ça marchait »).

**RÉGRESSION 2026-06-25** : `YZ_DIMENSION_AGENCE/METIER` (qui POSAIENT l'agence/métier avant) sont devenus rejetés par Yooz (changement côté Yooz) → l'import brouillon échouait en 400. Fix rev 0101 : retirés de `build_document_data` → import OK mais SANS agence/métier sur la ligne. Le vrai code data item reste introuvable : **~32 candidats testés** en brute-force (technique : envoyer 1 doc avec N champs candidats sur la ligne, fname `p.pdf` obligatoire sinon REQUEST_CONTENT_MULTI_PART_NOT_ALLOWED ; le 400 liste les `dataItemCodes` UNKNOWN → le candidat absent = valide ; un 400 ne crée PAS de doc, on peut sonder librement). Tous rejetés. L'export `EXPORT_DFM` passe par un **adaptateur custom `GroupeDFMAdapter`** (opaque). → seul le support Yooz / l'intégrateur DFM connaît le code. Question : « YZ_DIMENSION_AGENCE sur YZ_INVOICE_LINE ne marche plus (UNKNOWN_DATA_ITEM), quel est le code data item correct maintenant ? ».

**PREUVE 2026-06-25 (form config d'un doc)** : les codes SONT `YZ_DIMENSION_AGENCE` (dimensionId 2905050) et `YZ_DIMENSION_METIER` (dimensionId 2905049) — visibles dans le form de modif du bloc `YZ_INVOICE_LINE`. MAIS ce sont des data items **dynamiques** (clé `dimensionId`, pas `id`), ajoutés par l'org unit au CHARGEMENT du formulaire. Au `POST /documents` l'org unit n'est pas encore résolu → ces champs ne sont pas dans la config validée → `UNKNOWN_DATA_ITEM`. Donc **non settables à l'import initial**. Seules options : `runAutoAssignments=true` (règles Yooz post-création, mais agence = défaut/règle, pas l'agence calculée par client) OU modif post-création (form `/document/{yoozNumber}` ; `/feedbacks` public ne cible pas une ligne précise → ajoute une ligne). L'appli a un adaptateur custom `GroupeDFMAdapter` (onglet « Ecriture [GroupeDFM] »). → demander à l'intégrateur Yooz d'autoriser ces dims à l'import OU une règle d'auto-affectation agence basée sur le client. `runAutoAssignments=true` écrase aussi compte/TVA/libellé → garder **False** (rev 0103).

**API INTERNE v1 (mon token API y a accès)** pour poser agence/métier APRÈS création (impossible au POST /documents) :
- Lire un doc : `GET /yooz/v1/core/document/{yoozNumber}/open?isYoozNumber=true` (ou `&forceUpdate=true` pour éditer = pose un LOCK ; juste après création le doc est LOCKED qq sec → retry).
- Sauver : `PUT /yooz/v1/core/documents/{documentId}/forceModify` body `{document:{documentId,yoozNumber,data:{dataBlocks}}, formMessages:[...], documentAbandonChanges:false, isForceUpdate:true}`. documentId = id interne (≠ yoozNumber).
- Valeur dimension sur la ligne : `YZ_DIMENSION_AGENCE:{id:<elementId>}`, `YZ_DIMENSION_METIER:{id:...}`. Ids : CRE=1264664 TRO=1264668 AUB=1301022 STE=1288764 STP=1305050 LIL=1264665 ; métier 04(Info)=1264661 06=1264663 07=1275148 08=1303477 01=1264658.
- Code dans `yooz_client.yooz_set_line_dimensions()` + appelé par `submit_document(agence_code=...)`.
- **RÉSOLU (rev 0109)** : forceModify renvoyait `DISPLAY_MESSAGES_DIALOG` en boucle pour 2 raisons : (1) `YZ_ACCOUNTING_DATE` dans une période comptable FERMÉE (ex. 2026-02-13) → erreur bloquante `YZ_SF_R0508` → on force la date de compta à **aujourd'hui** (période ouverte) ; (2) le bon champ du body est **`saveAutoAssignments:false`** (réponse "Non" au popup "garder la logique"), PAS `documentAbandonChanges`. Body final : `{document:{documentId,yoozNumber,data}, formMessages:[], saveAutoAssignments:false, isForceUpdate:true}`. **Sauvegarde OK = HTTP 204** (pas 200). Testé : Créteil→CRE, Lille→Lille, métier 04. PDF doit être unique sinon DUPLICATE_FILE_ERROR. **rev 0110** : on garde la date de compta de la facture (choix Elliot) — si période fermée, la pose des dims échoue (dialog loop) mais le brouillon est créé ; pour les factures courantes la période est ouverte.

**EXPORT → SAGE (RÉSOLU + CONFIRMÉ DANS SAGE rev 0116, mécanisme capturé par Elliot en F12)** : chaîne complète auto OK = import brouillon → pose dims agence/métier → export SAGE ; vérifié 2026-06-29 (doc 74463 bien arrivé dans SAGE). : l'export SAGE = action MANUELLE « Exporter » (modèle EXPORT_DFM) = **`POST /yooz/v1/core/documents/exports`** body `{data:{dataBlocks:{YZ_MANUAL_EXPORT_SETTINGS:{YZ_MANUAL_EXPORT:{id:2183269}, YZ_MANUAL_EXPORT_LIST_CHOICE:{value:"SELECTED_DOCUMENTS_ONLY"}}}}, formMessages:[], isCalledFromIHM:true, documentIds:[<idInterne>], filters:[ft yoozNumber + contextual YZ_SYSTEM.YZ_CREATION_DATE], counter:1}` → **200 OK** → Yooz génère le fichier que l'Agent de Comm pousse dans SAGE. `id:2183269` = l'adaptateur GroupeDFM. Codé dans `yooz_client.yooz_export_to_sage()`, appelé par `submit_document` après la pose des dims. **rev 0118** : après un export OK, `submit_document` appelle aussi `yooz_force_terminate` (forceTask terminate) pour CLÔTURER le doc → il sort de la corbeille « Enregistrement » (sinon il y reste bien qu'exporté). Donc le terminate N'EST PAS une fausse piste pour la clôture — il l'est seulement pour l'export. Ordre : export PUIS terminate (terminer avant = doc removed = export échoue). **PISTES FAUSSES écartées** : (a) `documentTimeline` n'avance PAS le workflow ; (b) `documentFullyProcessed=true` → doc "no status" limbo ; (c) `forceTask` (`/documents/forceTask`, YZ_TASK="forceTerminateDocumentProcess", gridId -18, besoin filters+lastReloadGridDataDatetime sinon 500 SQL) = 201 mais ARCHIVE le doc sans l'envoyer en SAGE ; options forceTaskForm : Prise en charge=-12502_-12012, Enregistrement=-13002_-12002, Validation=-14002_-12004. (d) bug verrou : forceModify laissait le doc LOCKED → fix `GET /document/{id}/unlockDocument` après (rev 0114).

**Plan analytique DFM** = dimensionSet **1010** « Plan analytique par défaut », `relatedDimensions=["AGENCE","METIER"]` → **AXE01 = AGENCE, AXE02 = METIER** (rev 0000098). Codes réels via `GET /dimensionSets/1010/dimensions/{AGENCE|METIER}/data` (YZ_DIMENSION_DATA_COMMONS.YZ_CODE) : AGENCE = CRE Créteil/AUB/BRE/CHA/LIL/TRO/STE/STP… ; METIER = 04 Informatique, 06 Audiovisuel, 07 Fournitures, 08 IA, 01 Impression, etc. Vérifier réel via export CSV `GET /exportResults/{generatedFileId}` (export config `EXPORT_DFM`).

**Endpoints lisibles** (Bearer + header `applicationId`) : `GET /orgUnits`, `/orgUnits/{code}/dimensionSet`, `/documentTypes`, `/users`, `/exports`, `/dimensionSets/1010/dimensions/{axe}/data`. **PAS de GET document** (v2 n'expose pas la lecture de doc → lecture = exports fichiers). Le plan analytique n'est PAS exposé hors `/dimensionSets/.../data`.
